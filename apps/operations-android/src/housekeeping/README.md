# HB-158 SCR-66: assigned tasks and online status requests

This slice reads the current staff member's assigned tasks and sends explicit IN_PROGRESS/DONE requests using the existing real HB-148 endpoint. It does not complete whole HB-158: SCR-68 still depends on HB-150, and the published task request has no photo/upload field or attachment transport. Camera, money actions and the HB-159 offline queue remain unfinished.

Session resource clients pin the current token and session/property revision, use one attempt, and do not automatically refresh/replay a resource401. Session selection/token/logout signals clear private RAM views, invalidate the Writer and cancel pending transport. No access/PIN tokens or task catalogue are persisted. The existing refresh-token storage rule is unchanged. ApiClient normalizes header-provider failures as a network error; tests assert exact no-transport behavior when a pinned client becomes stale instead of inventing an exposed error category. The Writer's pre/post auth/me uses the resource transport; the Reader's existing auth profile behavior is unchanged.

Reads validate calendar dates, request `assignedTo` from current auth/me, exhaust unique cursor pages, and recheck the principal/role/scopes after all pages. Missing, partial, wrong-date/assignee or malformed projections never become visible data. Strict published task DTOs exclude guest, booking and payment fields. Server permission and property scope checks remain authoritative. Failures and logout clear the view; zero resolved items has an explicit empty state. Selecting a different input date invalidates the previous list.

## Online requests and recovery

The two buttons express user requests; the frontend has no transition table or inventory effect. The server checks current assignee/role/scope, legal status edge and If-Match under its Room/Task locks. No optimistic status or success message is produced. The list is invalidated before submit and on success/uncertainty; reload shows current facts without resolving an uncertain request.

Before PATCH, one minimal intent per principal is written through the existing native SecureStore adapter, under `housekeeping.pending.<userId>`. It contains task/room IDs, business date, desired status, version, UUIDv4 key, creation time and principal/role/scope/property context. It contains no task notes, room display code, guest data or tokens. This is an encrypted request record, not a cached task catalogue or an offline draft queue. QĐ-03's restriction on persistent session tokens remains unchanged. The native factory is only wired from the authenticated root; its writer is effect-owned and disposed on exit.

Storage operations serialize across mounted writers. Claim refuses to overwrite any different pending record, save failure sends no PATCH, and acknowledgement cleanup verifies the exact record. Restore never auto-sends. Within 24 hours the user may retry the same key, body and If-Match; new intents are blocked while unresolved. Unexpected DTO identity/status/version/ETag, network/protocol errors and cleanup errors preserve uncertainty. A first canonical business rejection can release its record; a rejected replay cannot erase an earlier ambiguous outcome. A key binding collision always requires review. A local review flag is stored without changing original request/binding fields, so reopening the coordinator cannot unlock a review-marked record. If writing that flag fails, the original request remains stored and the current coordinator stays blocked; subsequent recovery still requires fresh authorization and the same request within its replay window. A first 412 prompts a fresh explicit read and user intent, never automatic rebase.

After 24 hours, clock rollback, malformed/foreign records or an unresolved replay rejection, sending stays blocked and the record is retained for manual review. There is no authoritative command-result lookup/administrative recovery workflow in the published API; this slice does not infer success from a matching GET or delete records to bypass that gap. Changing context cannot replay the previous context's request. Local logout clears RAM immediately but deliberately keeps the encrypted owner-bound unresolved record so the same principal can recover after reauthentication.

The root's existing session stage opens this panel; the presentation is under src/ rather than an independent unauthenticated Expo route. Large lists use FlatList and existing ui-native tokens. A task card shows the business date as the calendar value `dd/MM/yyyy` (NFR-LOC-02): `formatBusinessDate` only reorders the ISO date-only string, never builds a `Date` or shifts by timezone, and the ISO business date sent to the API is unchanged. The date input and its label keep the `YYYY-MM-DD` request format. Maestro scenarios are `tests/maestro/hb158-assigned-task-read.yaml` and `tests/maestro/hb158-online-task-status.yaml`, supplied with synthetic STAFF_USERNAME/STAFF_PASSWORD and a fixture API reachable by the device. The write scenario additionally requires TASK_ID for an owned PENDING task dated 2026-11-01. Device/Maestro execution is BLOCKED when no Android device/tool exists; a Hermes bundle and real Session/Writer/controller TCP smoke are separate evidence. Unit presentation tests substitute only native host primitives/hooks and invoke the actual control callbacks with the real Reader/Writer/Session.
