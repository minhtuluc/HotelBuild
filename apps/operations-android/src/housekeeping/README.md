# HB-158 SCR-66: assigned-task read slice

This slice reads the current staff member's assigned tasks using the existing real HB-148 endpoint. It does not complete whole HB-158: SCR-68 still depends on HB-150, and the published task request has no photo/upload field or attachment transport. No camera prompt, mutation, money action or offline write queue is introduced.

Session resource clients pin the current token and session/property revision, use one attempt, and do not automatically refresh/replay a resource401. Session selection/token/logout signals clear the reader's private RAM projection and cancel pending reads. Access/PIN tokens and task data are not persisted. The existing refresh-token storage rule is unchanged. ApiClient normalizes header-provider failures as a network error; tests assert exact no-transport behavior when a pinned client becomes stale instead of inventing an exposed error category. Auth profile retains its existing refresh behavior.

Reads validate calendar dates, request `assignedTo` from current auth/me, exhaust unique cursor pages, and recheck the principal/role/scopes after all pages. Missing, partial, wrong-date/assignee or malformed projections never become visible data. Strict published task DTOs exclude guest, booking and payment fields. Server permission and property scope checks remain authoritative. Failures and logout clear the view; zero resolved items has an explicit empty state. Selecting a different input date invalidates the previous list.

The root's existing session stage opens this panel; the presentation is under src/ rather than an independent unauthenticated Expo route. Large lists use FlatList and existing ui-native tokens. The Maestro scenario is `tests/maestro/hb158-assigned-task-read.yaml`, supplied with synthetic STAFF_USERNAME/STAFF_PASSWORD and a fixture API reachable by the device. Device/Maestro execution is BLOCKED when no Android device/tool exists; a Hermes bundle and real Session/controller TCP smoke are separate evidence.
